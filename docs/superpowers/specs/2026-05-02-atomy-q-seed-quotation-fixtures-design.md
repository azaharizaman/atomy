# Atomy-Q Seed Quotation Fixtures Design

## Goal

Add a one-off fixture generation workflow for Atomy-Q quotation seed documents so quote-ingestion, OCR rerun, and normalization features can operate on stable PDF inputs instead of faker-driven paths and metadata.

The generated fixture set becomes the canonical source for seeded quotation PDFs and their document-linked metadata.

## Recommended Shape

Use a repo-managed fixture directory:

`apps/atomy-q/API/database/seed-data/quotations/`

The directory contains:

- `manifest.json`: deterministic fixture metadata keyed by stable business keys
- `files/`: generated PDF documents used by seeded quote submissions

This fixture set is generated by a one-off Artisan command, committed to the repository, and reused by future `migrate:fresh --seed` runs.

## Business Key Contract

Each seeded quotation fixture is keyed by a stable business key such as:

- `rfq-012/vendor-01`
- `rfq-012/vendor-02`
- `rfq-041/vendor-03`

Business keys are preferred over fixed `QuoteSubmission.id` values because they:

- keep the fixture set readable in the repository
- avoid coupling canonical filenames to database identifiers
- let the seeder remain deterministic while still creating database IDs normally
- make future fixture refreshes easier to review in diffs

The seeder owns the mapping from seeded RFQ/vendor combinations to these business keys.

## Manifest Contract

`manifest.json` should be machine-readable and deterministic. Each entry should include:

- `business_key`
- `rfq_key`
- `vendor_key`
- `pdf_path`
- `original_filename`
- `file_type`
- `vendor_name`
- `quote_status`
- `document_text`
- `line_seed_data`

`document_text` is the rendered quotation content used to produce the PDF and should remain truthful synthetic business data.

`line_seed_data` should hold the normalized source material needed to keep generated documents and seeded metadata aligned, such as:

- item descriptions
- quantities
- units of measure
- unit prices
- currency
- commercial terms

The manifest may also carry optional deterministic metadata for seeded workflow state when needed, but the first version should keep workflow-state derivation in the seeder unless the PDF content itself must explain it.

## PDF Requirements

The generated PDFs must be text-bearing documents, not image-only fake scans. The goal is to support ingestion, OCR rerun, and normalization testing with stable readable content.

Each PDF should include:

- supplier identity
- quotation reference
- RFQ reference
- quotation date
- buyer-facing line table
- currency
- subtotal or total
- delivery or payment terms

The PDFs should look like ordinary commercial quotations without imitating a real third-party company. Synthetic vendor identities seeded in Atomy-Q are acceptable because they are already fictional test data.

## One-Off Command

Add one operator-facing Artisan command in the API app, intended to be run only when the canonical fixture set needs to be created or refreshed.

Proposed command shape:

```bash
cd apps/atomy-q/API
php artisan atomy:generate-seed-quotation-fixtures
```

Responsibilities:

- build the canonical set of synthetic quotation payloads
- render deterministic PDFs into `database/seed-data/quotations/files/`
- write `database/seed-data/quotations/manifest.json`
- overwrite the same files cleanly on rerun

This command is not part of normal seeding. It is a maintenance tool for the canonical fixture set.

## Seeder Integration

`PetrochemicalTenantSeeder` should stop inventing quote document paths and metadata for seeded quotation submissions.

Instead it should:

- load the canonical fixture manifest
- resolve the expected business key for each seeded quote submission
- copy the matching fixture PDF into local storage under `storage/app/quote-submissions/...`
- persist a storage-relative `file_path`
- persist deterministic document-linked metadata from the manifest

This keeps `quote_submissions.file_path` compatible with the existing quote-ingestion adapters, which already resolve local storage paths for extraction and normalization flows.

## Faker Boundary

Factories and faker remain acceptable for models that do not directly reference the canonical quotation PDFs or their document-derived metadata.

For seeded quotation submissions and any metadata that must stay aligned with the fixture PDFs, faker should no longer be the source of truth.

That means seeded values tied to the quotation document should come from deterministic rules or the fixture manifest, including:

- file paths
- original filenames
- vendor-facing quotation references where used
- line descriptions if they must align with document content
- quantities, units, currency, and price values used by downstream normalization tests

## Architecture Boundaries

This work stays inside the API adapter/application layer:

- fixture generation command in `apps/atomy-q/API/app/Console/Commands`
- fixture definitions or support services in the API app
- seeder reads the manifest from `apps/atomy-q/API/database/seed-data/quotations/`

No new L1 package is required. This is repository-local seed and test-fixture infrastructure, not reusable domain logic.

## Verification

Verification should prove three things:

1. The one-off command deterministically regenerates the same manifest and PDFs.
2. `php artisan migrate:fresh --seed` produces quote submissions whose `file_path` points at real local PDFs copied from the canonical fixture set.
3. Existing quote-ingestion, OCR rerun, and normalization flows can consume those seeded PDFs without special-case code.

Recommended checks:

```bash
cd apps/atomy-q/API
php artisan atomy:generate-seed-quotation-fixtures
php artisan migrate:fresh --seed
php artisan test --filter QuoteIngestionIntelligenceTest
php artisan test --filter QuoteIngestionPipelineTest
```

## Non-Goals

- Backward-compatible support for older faker-generated seeded quotation documents
- A generic document-fixture framework for unrelated domains
- Provider-specific OCR tuning
- Reworking unrelated factories that are not tied to seeded quotation PDFs

## Risks And Controls

Risk: generated PDFs and manifest drift from seeded RFQ/vendor combinations.

Control: keep business-key generation in one deterministic mapping function and fail seeding loudly when a required fixture entry is missing.

Risk: fixture regeneration accidentally changes canonical PDFs without review.

Control: keep outputs in-repo so diffs are visible and reviewed.

Risk: seeded database metadata diverges from document content.

Control: derive document-linked metadata from the manifest, not faker.
